Decide if the stage moved, on the business's own pipeline (hartford-ai: Intro -> Discovery -> Scoped -> Policy Agreement -> Pilot Build -> Enablement -> Retainer/Live; jondal-capital: Sourced -> Outreach -> Engaged -> Materials Shared -> Due Diligence -> Committed -> Closed). STAGE CHANGES. For each clear change: update_deal_stage with a one-line reason citing the email (sender, date, what it said), then log_activity, then refresh the DEAL RECORD's own narrative so it never contradicts its new stage: upsert_deal for the same deal, rewriting next_step to the action the new stage implies and PREPENDING to notes a dated block ("<date> (morning routine, stage change): <from> -> <to>. MATERIAL UPDATES WITH NO STAGE CHANGE. The step above handles email that moves a stage. This step handles everything else, because an email that does not move a stage can still change what is true about a deal, and a CRM that records nothing in that case goes stale while looking maintained. For every email you matched to a deal but did not act on as a stage change, decide whether it is MATERIAL. It is material if at least one of these holds: it resolves, closes, or supersedes something named in that deal's next_step; it changes a date, an amount, a scope, or a named commitment; it introduces or clears a blocker; or the counterparty states a status that the deal record currently contradicts. It is NOT material if it is pleasantries, thanks, scheduling chatter, a newsletter, or a restatement of something already recorded. For each MATERIAL email: (a) call log_activity against the deal, direction inbound, with a one-line gist citing sender and date, so lastActivityAt reflects the real last contact and detect_stale_items stops measuring from a wrong date; (b) where the email resolved or changed an open item, call upsert_deal to rewrite next_step to what is genuinely outstanding now, and PREPEND to notes a dated block ("<date> (morning routine, material update, no stage change): <what changed>. Evidence: <sender, date, gist>.") keeping all prior text. NEVER touch stage in this step, not by one position. The premise of this step is that the evidence did not justify a stage move, so a stage written here would be a stage written without evidence. Terminal stages (hartford-ai Retainer/Live, jondal-capital Closed) have nowhere forward to go, so the stage-change step can never fire for them and this step is the ONLY way they are ever updated from email. Never treat "no stage available to advance to" as "nothing worth recording." Keep two lists for the brief, the mirror, and the archive: the deals you updated here with what changed, and the matched emails you judged non-material and skipped.

Part 2 - Sweep for stranded meetings
List Otter meetings from the last 48 hours (Otter search with created_after). For each, call CloseDeals check_processed_transcript with its Otter id. Already processed: skip.

For each UNPROCESSED meeting, try ONE Otter fetch of the full transcript, then branch:

Full transcript servable: the meeting was stranded by the processing race and can now be handled. Queue a re-fire request for it, one line per meeting, in EXACTLY this format (the n8n relay parses these): REFIRE-REQUEST: <meeting title> | https://otter.ai/u/<meeting id> You make no network calls and hold no credentials; the n8n re-fire relay watches the brief for these lines and fires the follow-up routine for each.
Still no transcript and the meeting is OLDER than 48 hours: mark it needs-human in the brief (likely a failed recording on Otter's side; the owner should check it in the Otter app).
Still no transcript and YOUNGER than 48 hours: note it as pending; tomorrow's sweep will retry.
Keep the sweep list for the brief: re-fire requested (title + id), pending, needs-human.

Part 3 - Read the Outlook calendar and sync it into CloseDeals
The brief's meeting list comes from the Microsoft 365 Outlook calendar. That is the only calendar this account has. There is no Google Calendar and no Google Calendar connector; never go looking for one, and never let its absence turn into a report of no meetings.

1. Compute the window in America/New_York: today at local 00:00 through the day after tomorrow at local 00:00, half-open. Write both bounds as RFC 3339 with the offset actually in effect that date (-04:00 on EDT dates, -05:00 on EST dates). Outlook returns each event as a wall-clock dateTime plus a named timeZone; convert using that pair. Never treat an Outlook wall-clock string as UTC, and never send a bare wall-clock time to CloseDeals.

2. Query outlook_calendar_search with query "*", afterDateTime and beforeDateTime set to that window, limit 25, order "oldest". afterDateTime filters on event start and beforeDateTime on event end, so widen each bound by a day and discard out-of-window events after you read them; that way a meeting straddling midnight is not silently dropped. If the response ends with an item carrying nextOffset, call again with that offset and keep going until no nextOffset comes back. Record the raw provider count as items_found and whether pagination ran to exhaustion.

3. Read every event you kept with read_resource on its calendar:///events/{id} URI. The full read is what gives you the authoritative attendee list, the opaque calendar id, and meetingTranscriptUrl on Teams meetings. Keep every provider id and the connector's own webLink exactly as returned. Never construct a URL yourself.

4. Normalize each event: title trimmed of stray whitespace; start and end as RFC 3339 with the numeric offset; attendees from the full read; is_internal_only true only when every attendee address is on umergence.com, which includes a solo event holding only your own address; user_response_status from the event's showAs or your own attendee response; calendar_status one of confirmed, tentative, cancelled.

5. Sync every event that is NOT cancelled through sync_calendar_event, one call per event, with calendar_provider set explicitly to "microsoft_365". That argument defaults to "google_calendar" when omitted, which files the meeting under a provider this account does not have and leaves the brief reading an empty store. It is never optional. Pass with it: calendar_event_id (the opaque provider id, case-sensitive), title, start, end, location, conference_link, calendar_status, is_all_day, is_internal_only, user_response_status, attendees with is_internal set per attendee, attendees_complete true (you did the full read), user_email_domains ["umergence.com"], source_calendar_id (the calendar id from the full read), source_account_id "Elijah.Gutman@umergence.com", and source_url (the connector's webLink). Cancelled events are not synced: count them in items_found, leave them out of the payload, and leave them out of items_supplied.

6. Build the calendar_sources ledger, one row for the one expected provider and account: provider "microsoft_365", account_id "Elijah.Gutman@umergence.com", query_range_start and query_range_end as computed, resources_queried holding the opaque calendar id from the full read, resource_enumeration_complete true (the connector exposes one default mailbox calendar and offers no calendar-enumeration tool, so querying it is full coverage), pagination_complete true only if you followed every nextOffset, full_reads_complete true only if you read every event you supplied, items_found the raw provider count, items_supplied the count of events actually in your calendar_events payload. Set query_status "complete" only when enumeration, pagination and full reads all ran clean; "partial" when any of them was capped or skipped; "unavailable" or "failed" with error_code when the connector errored. items_supplied must equal the number of events you pass, or the brief records a source_item_attribution_mismatch; cancelled events are dropped server-side, so never count them in it.

7. Sanity check before generating. If outlook_calendar_search returned events for today but get_todays_meetings comes back empty, the sync did not land. The overwhelmingly likely cause is a missing or wrong calendar_provider. Fix it and re-sync. Do not proceed to report an empty day.

An empty calendar is reportable as zero meetings ONLY when query_status is "complete". Omitted, partial, unavailable and failed all mean unverified: say plainly that the calendar could not be verified and why. "No meetings detected" is never the right sentence for an unverified calendar.
